📋 Planejamento em 5 Etapas Sequenciais

  • Etapa 1 (Dados & ML Offline): Unificação das 5 tabelas Azure (`telemetry`, `machines`, `failures`, `errors`, `maint`), divisão Treino (70%) / Validação (15%) / Teste (15%) e exportação do `Pipeline` em `models/model.joblib`.
  • Etapa 2 (Persistência & Contratos): Criação das tabelas `prediction_logs` e `email_alert_logs` no SQLite e definição dos schemas Pydantic com restrições físicas estritas (`Field`).
  • Etapa 3 (Ciclo de Vida Lifespan): Carregamento único do artefato em memória RAM no startup da API.
  • Etapa 4 (Rotas & Idempotência): Construção dos endpoints `/health`, `/predict`, `/v1/predict`, `/motors/status` e `/alerts` com tratamento semântico de exceções HTTP (`200`, `400`, `422`, `500`, `503`).
  • Etapa 5 (Qualidade & Documentação): Testes automatizados com Pytest, Simulador Web com Chart.js e documentação no `README.md`.

Fases 1, 3, 4 e 5 — Explicação do Código

"Aqui estão os 4 pilares técnicos do código: (1) Na Fase 1, encapsulei o SimpleImputer, o StandardScaler, o OneHotEncoder e o RandomForestRegressor em um único Pipeline do Scikit-Learn, evitando vazamento de dados entre treino, validação e teste. (2) Na Fase 3, usei @asynccontextmanager com lifespan no FastAPI para carregar o arquivo .joblib uma única vez na memória RAM durante o startup, cumprindo a proibição de leitura de disco a cada requisição. (3) Na Fase 4, apliquei validação estrita com Field(gt=0, le=..., pattern=...) no Pydantic. E (4) Na Fase 5, tratei os status HTTP e implementei idempotência com SQLite."

1. Fase 1: Pipeline Scikit-Learn (src/services/ml_service.py)

def build_preprocessing_and_model_pipeline(n_estimators=150, max_depth=16, min_samples_leaf=2):
    numeric_transformer = Pipeline(steps=[
        ("imputer", SimpleImputer(strategy="median")),
        ("scaler", StandardScaler())
    ])
    categorical_transformer = Pipeline(steps=[
        ("imputer", SimpleImputer(strategy="most_frequent")),
        ("encoder", OneHotEncoder(handle_unknown="ignore", sparse_output=False))
    ])
    preprocessor = ColumnTransformer(transformers=[
        ("num", numeric_transformer, NUMERICAL_FEATURES),
        ("cat", categorical_transformer, CATEGORICAL_FEATURES)
    ])
    return Pipeline(steps=[
        ("preprocessor", preprocessor),
        ("regressor", RandomForestRegressor(n_estimators=n_estimators, max_depth=max_depth))
    ])

2. Fase 3: Ciclo de Vida em RAM — Lifespan (src/main.py)

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Executado UMA ÚNICA VEZ na inicialização do servidor ASGI
    Base.metadata.create_all(bind=engine)
    model = load_model_on_startup()  # Carrega models/model.joblib na RAM
    app.state.model = model
    yield
    # Executado no desligamento (shutdown) para liberar recursos
    clear_model_cache()

app = FastAPI(title="API de Manutenção Preditiva", lifespan=lifespan)

Visão Crítica e Evolução de MLOps
🎙️ Roteiro sugerido para falar neste slide (7:30 – 8:30)

"Para concluir: embora o sistema cumpra 100% dos requisitos funcionais e arquiteturais do projeto — incluindo pipeline serializado, carregamento em RAM via lifespan, validação Pydantic, persistência SQLite com idempotência e testes automatizados —, em um cenário industrial de larga escala eu implementaria três melhorias futuras: (1) testar modelos baseados em Gradient Boosting (como LightGBM/XGBoost) ou redes LSTM para capturar dependências temporais mais longas; (2) adicionar monitoramento contínuo de Data Drift e Model Drift em produção; e (3) migrar o banco local SQLite para PostgreSQL/TimescaleDB com autenticação JWT nos endpoints. Muito obrigado!"

📈 1. Evolução da Modelagem Preditiva

O RandomForestRegressor otimizado atingiu 99,03% de Acurácia / F1-Score nas faixas operacionais e R² = 0,9957 (MAE = 3,43h) no conjunto de teste. Como próximo passo em larga escala, poderíamos experimentar:

  • XGBoost / LightGBM com otimização Bayesiana de hiperparâmetros (Optuna).
  • Redes Recorrentes (LSTM / Temporal Fusion Transformers) utilizando janelas deslizantes de 48h e 72h de telemetria contínua.

🔍 2. Monitoramento de Data & Concept Drift

Em plantas industriais, o envelhecimento mecânico altera a distribuição estatística dos sensores ao longo dos meses:

  • Integrar EvidentlyAI ou Prometheus + Grafana sobre a tabela prediction_logs.
  • Disparar retreinamento automático do pipeline no MLflow quando for detectado desvio estatístico (drift) nas variáveis de entrada.

🔐 3. Segurança e Escalabilidade de Banco

Para suportar milhares de motores enviando telemetria simultaneamente via gateways IoT:

  • Migrar do SQLite local para PostgreSQL / TimescaleDB dedicado a séries temporais.
  • Adicionar autenticação via API Key / OAuth2 JWT e controle de Rate Limiting nos endpoints de inferência.
